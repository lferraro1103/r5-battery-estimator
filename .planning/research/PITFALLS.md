# Domain Pitfalls

**Domain:** Windows tray application that reads vendor HID battery telemetry and learns per-profile runtime estimates for the Attack Shark R5 Ultra
**Researched:** 2026-09-28
**Overall confidence:** MEDIUM — platform behavior is grounded in official Microsoft, SQLite, and project documentation; the mouse firmware's percentage granularity, charging transitions, and coexistence behavior still require hardware soak tests.

## Roadmap Phase Vocabulary

The phase mappings below are recommendations for roadmap construction, not existing phase numbers.

| Phase | Purpose |
|-------|---------|
| **A. Protocol characterization** | Freeze protocol fixtures, measure percentage granularity/staleness, charging behavior, and vendor-app coexistence on the real mouse. |
| **B. Reliable collector and lifecycle** | Build single-instance HID ownership, serialized reads, disconnect/reconnect, suspend/resume, and raw observation capture. |
| **C. Durable event model and profiles** | Define observation eligibility, cycle boundaries, canonical profile identity, migrations, and recovery. |
| **D. Estimator and confidence** | Fit separate scenario models, account for censored/quantized data, validate uncertainty, and detect drift. |
| **E. Tray, startup, and alerts** | Add the tray lifecycle, startup state, detailed UI, and deduplicated notifications on top of trustworthy domain state. |
| **F. Soak validation and release hardening** | Exercise long runtimes, sleep, unplug/replug, charging, vendor software, upgrades, corruption, and notification behavior. |

## Critical Pitfalls

Mistakes in this section can invalidate the learned model, interfere with the mouse, or force a storage/architecture rewrite.

### Pitfall 1: Treating the firmware percentage as a precise, continuous measurement

**What goes wrong:** The estimator differentiates consecutive readings as though `90%` were an exact value that changed exactly when first observed. Plateaus produce an apparent zero drain rate, a later step produces an apparent spike, and the displayed remaining time oscillates or becomes implausibly precise.

**Why it happens:** The spike proves that the receiver returns a device-reported integer and that five consecutive queries returned 90%; it does not establish resolution, update cadence, rounding direction, accuracy, or whether the value is cached. Quantization itself is a measurement uncertainty source. A repeated value is usually the same coarse observation, not new independent evidence.

**Warning signs:**

- A histogram of deltas contains almost entirely zeroes plus fixed jumps such as 5 or 10 percentage points.
- The first estimate after a jump differs drastically from the estimate during the preceding plateau.
- Confidence rises with poll count even though no percentage boundary was crossed.
- Reported percentage briefly rises while `charging=false`, especially after rest or a charge transition.
- Estimated discharge rate changes materially when only the polling interval changes.

**Prevention:** Preserve every raw reply, but model the reported percentage as a quantized interval with an unknown threshold-crossing time. Infer rate from sufficiently long, eligible spans and percentage transitions rather than from per-poll derivatives. Learn the actual step-size and refresh behavior during Phase A before choosing estimator thresholds. Keep UI language explicit: “device-reported percentage” is distinct from learned runtime.

**Recovery:** Rebuild derived models from retained raw events using quantization-aware logic; invalidate confidence generated by the old per-sample method. If raw events were discarded, reset calibration instead of attempting to repair biased aggregates.

**Phase mapping:** Phase A must characterize step size and staleness; Phase C must retain raw observations and eligibility metadata; Phase D must implement interval-aware estimation and display uncertainty.

**Confidence:** HIGH for the risk pattern; MEDIUM for its magnitude on this specific firmware until a full discharge is observed.

### Pitfall 2: Converting interval-censored observations into exact discharge events

**What goes wrong:** If the app saw 90% at 10:00 and 80% at 12:00, it assigns the entire change to 12:00 or assumes it occurred uniformly across the two hours. The same error occurs across app shutdown, receiver disconnect, unknown settings, or missing samples. Rates become biased, change points are misplaced, and later profile attribution becomes impossible to repair.

**Why it happens:** Percentage boundaries are crossed at unknown times between readouts. Gaps often contain unobserved state changes. NIST classifies this shape of information as readout/interval-censored data; exact-event methods are not valid substitutes merely because both endpoints are known.

**Warning signs:**

- Database rows record a synthetic “10% consumed at 12:00” event without lower/upper time bounds.
- Long gaps contribute as much certainty as continuous observation.
- A percentage drop spanning two profile IDs is credited entirely to one profile.
- Closing the app for hours and reopening causes a large instantaneous rate spike.
- Tests contain only evenly sampled, fully observed traces.

**Prevention:** Store observation intervals with start/end readings, wall-clock bounds, awake-time exposure, connectivity, power state, charging state, profile identity, and an eligibility reason. Split at every known state boundary. If a gap contains ambiguous states, keep it as censored evidence or exclude it from fitting; do not manufacture precision. Test irregular sampling, missing endpoints, and skipped firmware steps.

**Recovery:** Mark previously ambiguous intervals ineligible and refit from unambiguous spans. Where legacy rows lack enough provenance to reconstruct bounds, lower or reset the affected profile's confidence.

**Phase mapping:** Phase B establishes segment boundaries; Phase C encodes censored intervals and exclusion reasons; Phase D uses appropriate likelihood/robust aggregation; Phase F validates recovery after intentionally missing observations.

**Confidence:** HIGH.

### Pitfall 3: Mixing active play, ordinary use, idle, charging, and disconnected time into one rate

**What goes wrong:** “Everyday” and “continuous gaming” estimates converge to the same blended number, or both are wrong. Overnight idle time makes gaming runtime look excellent; a charging interval can create negative drain; disconnected time is treated as zero consumption; and a charge/reset boundary is interpreted as battery recovery.

**Why it happens:** Wall-clock duration is easy to compute, but it is not exposure to a single discharge regime. The requested outputs describe two different scenarios, while firmware percentage alone cannot identify whether the mouse was active. Charging and post-charge relaxation are different processes from discharge.

**Warning signs:**

- Continuous-gaming runtime improves after the computer sits unused overnight.
- Estimated drain becomes zero or negative around a cable connection.
- Everyday and gaming estimates differ only by a fixed cosmetic multiplier.
- The model labels a plateau as “idle” solely because the coarse percentage did not change.
- A full or partial top-up is included in the same regression window as discharge.

**Prevention:** Define a state machine before fitting: `discharging-active`, `discharging-idle`, `charging`, `post-charge-quarantine`, `sleep-gap`, `disconnected`, and `unknown`. Determine activity independently of the battery value; otherwise a plateau cannot distinguish true idle from coarse quantization. Fit scenario estimates from their corresponding exposure or explicitly state the assumed active/idle mixture. End or censor a discharge segment at every charge indication, upward jump, disconnect, suspend boundary, or profile ambiguity. Require stable discharging readings after unplug before re-admitting data.

**Recovery:** Reclassify raw segments with the state machine and rebuild models. If activity provenance was never stored, use only clearly labeled sessions for “gaming” and present everyday estimates as provisional rather than inventing a split.

**Phase mapping:** Phase A measures charging-flag lag and rebound; Phase B records independent activity and lifecycle signals; Phase C enforces eligibility; Phase D builds separate scenario models.

**Confidence:** HIGH for separation requirements; MEDIUM for the quarantine duration, which must be measured on-device.

### Pitfall 4: Letting automatic profile creation fragment the data

**What goes wrong:** Transient read failures, inconsistent units, boolean encoding differences, or settings changing one field at a time create dozens of numbered profiles. Each profile has too little data to learn, startup selects the wrong one, and equivalent configurations never share evidence.

**Why it happens:** Automatic identity is attractive because it removes profile management, but every raw settings snapshot is not necessarily a stable semantic configuration. Missing values are particularly dangerous: treating `unknown` as a new value creates profiles for telemetry failures.

**Warning signs:**

- More than a few profile creations per day without deliberate user changes.
- Profiles exist for only one or two samples.
- Two profile keys differ only by representation such as `1` versus `true`, ordering, or units.
- Startup repeatedly creates a new profile before the vendor settings are fully readable.
- `Revisar perfil` produces a new profile without a real setting change.

**Prevention:** Canonicalize exactly the four approved dimensions: polling rate, Competitive Mode, Motion Sync, and sleep time. Normalize types and units, sort fields, version the key format, and hash the canonical form. Require a stable snapshot across multiple reads or a debounce interval before switching/creating. An unreadable field means “profile unknown; pause attribution,” never “new profile.” Record raw and normalized values for diagnostics. Test startup while the receiver and vendor software are still initializing.

**Recovery:** Add an internal migration that maps equivalent keys, reassigns raw observations, merges derived evidence, and preserves an audit trail. Do not expose manual merge/delete controls merely to compensate for unstable identity logic.

**Phase mapping:** Phase A documents settings read semantics; Phase C owns canonicalization, debounce, and migration; Phase D refuses to train on unknown-profile intervals; Phase F soak-tests repeated startup and manual review.

**Confidence:** HIGH.

### Pitfall 5: Reporting confidence from sample count instead of independent information

**What goes wrong:** Polling 90% one hundred times produces “high confidence” despite no observed transition. The UI shows a narrow ETA that is wrong under the next real session, undermining the product's core promise.

**Why it happens:** Rows are easy to count. Effective information instead comes from elapsed eligible exposure, observed percentage transitions, coverage across charge levels, distinct sessions/cycles, recency, and out-of-sample error. Correlated samples and quantized repeats do not add equivalent evidence.

**Warning signs:**

- Confidence rises while percentage and profile remain unchanged.
- A profile becomes “calibrated” after one partial session.
- Prediction intervals shrink monotonically even when residual error worsens.
- The displayed ETA changes by hours without a corresponding confidence downgrade.
- Nominal intervals miss held-out outcomes far more often than their label implies.

**Prevention:** Define confidence as a calibration contract, not a progress bar. Gate it on distinct transitions, eligible awake exposure, number of independent sessions, percentage-range coverage, and recent holdout error. Backtest time remaining at historical cut points without training on future observations. Prefer qualitative tiers plus a range until empirical coverage supports numeric precision. Clamp or suppress ETA when the remaining percentage is below the model's observed range.

**Recovery:** Widen intervals immediately, downgrade affected profiles, and recompute confidence from stored evidence. Preserve the point estimate only if it remains useful; never preserve a misleading confidence label for UI continuity.

**Phase mapping:** Phase D owns the confidence contract and temporal backtests; Phase E must render provisional/calibrating states honestly; Phase F sets release gates for coverage and stability.

**Confidence:** HIGH.

### Pitfall 6: Allowing more than one HID owner or overlapping feature-report transactions

**What goes wrong:** A duplicate tray process, the official Attack Shark application, a settings refresh, and the polling loop issue overlapping operations. Opens fail with sharing violations, replies are matched to the wrong request, the mouse becomes temporarily unavailable, or input latency increases during play.

**Why it happens:** Windows device handles obey access/share-mode compatibility. Vendor protocols may also assume request/response serialization even when the OS permits multiple opens. `node-hid` warns that enumeration/open operations are relatively costly and that parallel HID work can slow other USB activity.

**Warning signs:**

- `ERROR_SHARING_VIOLATION`, intermittent open failures, short/malformed replies, or unexpected protocol prefixes.
- Problems occur only while the vendor app is open or only immediately after sign-in.
- Two tray icons or two processes appear after startup plus manual launch.
- Poll duration overlaps the next scheduled poll.
- Mouse latency or USB activity changes when profile review or device enumeration runs.

**Prevention:** Enforce one application instance per user before opening HID. Route every battery/settings operation through one serialized, cancellable command queue and one long-lived handle where practical. Give operations timeouts; never start a second operation because the first is slow. Enumerate on startup, device notification, or bounded recovery—not on every poll. Test coexistence with the official app and define a non-destructive “temporarily unavailable because another app owns the device” state. Measure latency at the highest polling-rate/Competitive configuration.

**Recovery:** Cancel queued work, close the handle, back off with jitter, re-enumerate the validated interface, and resume with a fresh segment. Do not count failures as battery readings or immediately hammer reopen in a tight loop.

**Phase mapping:** Phase A validates vendor-app coexistence and protocol framing; Phase B implements single-instance ownership and serialization; Phase F runs contention and latency soak tests.

**Confidence:** HIGH for Windows/node-hid behavior; MEDIUM for the R5 Ultra firmware's tolerance of cross-process access until tested.

### Pitfall 7: Treating disconnect, receiver sleep, stale handles, and protocol mismatch as “0% battery”

**What goes wrong:** A failed query becomes zero, fires a low-battery notification, and poisons the learned rate. After reconnect, the app continues using a stale device path or opens the wrong HID collection that shares the VID/PID.

**Why it happens:** USB device paths and handles are lifecycle-bound. The spike found multiple vendor interfaces and only interface 2 accepted the expected report. A VID/PID match alone is insufficient validation, and absence of telemetry is not a battery measurement.

**Warning signs:**

- Sudden 0% immediately followed by the prior percentage.
- Reconnect works only after restarting the application.
- Battery parsing accepts replies without checking the `A1 / 02 / 83` structure and length.
- Repeated enumeration continues while the receiver is absent.
- The UI keeps showing an old percentage without its age or connection status.

**Prevention:** Represent `connected`, `telemetry unavailable`, `device asleep`, `disconnected`, and `invalid response` separately. Validate interface, report length, marker bytes, charging domain, and `0..100` percentage before admission. Subscribe to device arrival/removal, close on error/removal, and re-enumerate with bounded exponential backoff. Display the age of the last valid sample and never substitute a sentinel number into the measurement field.

**Recovery:** Discard the failed interval, reopen a newly enumerated and protocol-validated path, start a new segment, and only clear degraded UI state after multiple valid replies.

**Phase mapping:** Phase A freezes good/bad response fixtures; Phase B owns the connection state machine; Phase C prevents invalid readings from entering learning; Phase E communicates staleness; Phase F tests unplug, receiver sleep, and reconnect loops.

**Confidence:** HIGH.

### Pitfall 8: Using one clock across Windows sleep, hibernate, clock adjustment, and resume

**What goes wrong:** An overnight suspend becomes hours of “active” discharge, a wall-clock correction creates negative duration, or resume attributes a stale post-sleep percentage to the preceding active profile. Estimates change dramatically based on laptop sleep habits rather than mouse use.

**Why it happens:** Microsoft documents that `GetTickCount64` includes sleep/hibernate while unbiased interrupt time counts only working-state time. Normal suspend sends power events, but critical suspension may provide no advance notification. Automatic wakes and user resumes also differ, so a single callback is not sufficient.

**Warning signs:**

- Negative or extremely large sample durations.
- A large percentage change is timestamped immediately on resume.
- Active drain is lower for users who suspend frequently.
- The collector assumes every suspend event has a matching pre-suspend flush.
- Tests cover normal sleep but not hibernate, critical termination, or a missed callback.

**Prevention:** Store UTC wall time for chronology and a monotonic working-state clock for awake exposure. Segment explicitly on suspend/resume and also when observed clock deltas or poll gaps exceed a threshold, covering missed events. Persist atomically before returning from power handlers; Microsoft allows little time and critical suspension may skip advance notice. On resume, reopen/validate HID as needed and quarantine the first reading from active-rate learning. If sleep drain is later modeled, treat it as its own regime using the wall-minus-awake interval.

**Recovery:** Reclassify spans containing sleep as censored or sleep-regime data, refit active models, and downgrade confidence where legacy records lack both clocks.

**Phase mapping:** Phase B implements dual clocks and power-event segmentation; Phase C stores both exposures; Phase D keeps sleep separate; Phase F runs real sleep/hibernate/resume soak tests.

**Confidence:** HIGH.

### Pitfall 9: Making derived aggregates the only durable data

**What goes wrong:** A later fix to quantization, eligibility, or profile identity cannot repair learned rates because only averages were stored. A crash during an in-place update corrupts the sole calibration file, or a schema upgrade partially applies and the tray app silently starts over.

**Why it happens:** A local-only application can look too small to need an event ledger, migration discipline, or recovery plan. Yet the estimator is expected to improve over weeks and every early modeling assumption is likely to change after hardware validation.

**Warning signs:**

- The database stores `averageDrain` and `sampleCount` but not raw observations and exclusion reasons.
- Migration code performs multiple changes without one transaction or a recorded schema version.
- Two processes can write the same store.
- Backup copies only the main SQLite file while WAL mode is active.
- Corruption or an unsupported downgrade causes silent deletion/reinitialization.

**Prevention:** Keep an append-oriented raw observation/event table as the source of truth and treat profiles, cycles, and rates as rebuildable projections. Use one writer, transactional inserts/migrations, constraints, explicit application/schema version, and startup integrity checks. Create a safe pre-migration backup with the database's supported backup mechanism. If SQLite WAL is selected, preserve its sidecar semantics and verify the bundled SQLite includes the March 2026 WAL-reset fix (3.51.3 or an official patched backport) before permitting multiple connections that can write/checkpoint.

**Recovery:** Quarantine the damaged store, retain it for diagnostics, restore the last verified backup, and replay valid raw events to rebuild projections. Offer export/reset rather than silently fabricating a clean history. Refuse a destructive downgrade when the installed app cannot understand the newer schema.

**Phase mapping:** Phase C owns the event schema, migrations, backup, integrity, and rebuild path; Phase F crash-tests writes and upgrades before release.

**Confidence:** HIGH for the architecture risk; MEDIUM for SQLite-specific details until the storage stack is selected.

## Moderate Pitfalls

### Pitfall 10: Assuming startup registration guarantees continuous background collection

**What goes wrong:** The application says “start with Windows” but is disabled in Task Manager, never registered after install, points at an old executable path after update, or launches twice. Missing history is then interpreted as continuous observation.

**Warning signs:** Startup state in the UI disagrees with Task Manager; the app never runs after a fresh install until manually opened; duplicate tray processes appear; the first sample after sign-in is delayed by heavy startup work.

**Prevention:** Treat startup as queryable, user-controlled state. Microsoft documents that a startup task disabled by the user cannot be programmatically re-enabled. Register/request once through the chosen packaging mechanism, report the actual state, provide instructions for manual re-enable, and never “repair” the user's choice. Keep startup initialization below the high-impact thresholds, acquire the single-instance guard first, and defer nonessential analysis.

**Recovery:** Detect the disabled/broken state in the detailed UI, offer a user-initiated repair path appropriate to the installer, and mark the missing period as unobserved rather than backfilling it.

**Phase mapping:** Phase E implements startup state and user messaging; Phase F tests fresh install, disabled startup, update path, and simultaneous manual launch.

**Confidence:** HIGH.

### Pitfall 11: Re-alerting on every low-battery poll or assuming toast delivery is guaranteed

**What goes wrong:** A coarse value remains at 15% for hours and triggers repeated alerts. The user disables notifications, while Focus Assist can suppress a genuinely useful warning. A value bouncing around the threshold repeatedly re-arms the alert.

**Warning signs:** Multiple alerts within one discharge segment; alerts repeat after app restart at the same level; notification count scales with polling frequency; there is no persistent low-battery state in the tray/window.

**Prevention:** Trigger on a downward threshold crossing, persist the alert decision, and deduplicate per discharge cycle. Add hysteresis: re-arm only after a clear recharge above a higher boundary or a new validated cycle. Optionally escalate once at a materially lower threshold; do not use urgent/Focus-bypass behavior by default. Keep the tray icon and detailed UI as the durable truth because Windows may suppress popups. Respect the configured threshold and provide a quiet/testable notification policy.

**Recovery:** Clear stale queued notifications, retain the current low state without replaying every missed alert, and reset the alert latch only after verified recharge/hysteresis.

**Phase mapping:** Phase C defines charge-cycle and alert-latch state; Phase E implements UX; Phase F tests plateau, restart, threshold bounce, Focus Assist, and charging re-arm.

**Confidence:** HIGH.

### Pitfall 12: Losing the tray icon when Explorer restarts or conflating a hidden icon with a stopped collector

**What goes wrong:** The process continues collecting but its icon disappears after Explorer/taskbar recreation, or the user hides the icon and assumes the app stopped. Conversely, a visible stale icon suggests collection is healthy when HID access has failed.

**Warning signs:** Killing/restarting Explorer removes the icon until app restart; two icons appear after recreation; tooltip data stops updating while the process remains alive; startup diagnostics equate icon visibility with collector health.

**Prevention:** Use a stable icon identifier, add it once, set the supported notification-icon version after every add, and handle the registered `TaskbarCreated` broadcast by re-adding idempotently. Microsoft notes that taskbar recreation removes application-added icons. Separate process health, collector state, and shell visibility in diagnostics. Show stale/disconnected status in the icon/tooltip when available.

**Recovery:** Recreate the icon on the shell broadcast without restarting the collector; if icon registration fails, continue safe collection and expose a diagnostic/logged degraded UI state.

**Phase mapping:** Phase E owns tray lifecycle; Phase F restarts Explorer, changes DPI, and tests user-hidden overflow behavior.

**Confidence:** HIGH.

### Pitfall 13: Polling or enumerating aggressively enough to perturb gameplay

**What goes wrong:** The monitoring tool consumes USB/CPU resources or competes with vendor HID traffic, violating the requirement not to affect mouse latency. More samples do not improve information when the firmware value is unchanged.

**Warning signs:** USB enumeration appears on every timer tick; CPU wakeups remain high while idle; feature-report calls overlap; gameplay latency correlates with settings refresh; lowering the poll rate does not reduce estimator accuracy.

**Prevention:** Separate lightweight battery polling from expensive enumeration and full settings refresh. Use adaptive cadence: slower on stable plateaus/idle or absent device, immediate one-shot refresh on user action/reconnect/resume, and bounded faster confirmation only around state transitions. Use async operations, serialize them, measure execution time and resource use, and fail closed to a slower cadence on repeated errors.

**Recovery:** Remotely impossible in a local-only app, so ship a conservative default cadence and a diagnostic kill switch. If latency is observed, suspend profile refresh first, increase backoff, and preserve existing estimates rather than continuing aggressive reads.

**Phase mapping:** Phase A benchmarks query cost; Phase B implements scheduling/backpressure; Phase F validates CPU wakeups and gameplay behavior at worst-case mouse settings.

**Confidence:** HIGH for enumeration cost; MEDIUM for perceptible gameplay impact until measured.

### Pitfall 14: Treating every charge session as a clean calibration cycle

**What goes wrong:** A five-minute top-up is labeled a full cycle, `100%` is assumed even when never observed, or data immediately after unplug is used to reset capacity. Cycle-based confidence and aging estimates become meaningless.

**Warning signs:** Cycle count increases on every cable connection; a cycle begins without a validated charge transition; full-capacity calibration occurs below 100%; partial charges cause abrupt changes to all runtime estimates.

**Prevention:** Model charge sessions and discharge segments separately. A “full calibration cycle” requires explicit evidence defined after Phase A (for example, stable full indication plus a later eligible discharge range), while partial top-ups simply start a new segment with known/unknown initial percentage. Never infer energy added from percentage rise during charging. Preserve charge start/end, maximum observed percentage, flag transitions, and quarantine status.

**Recovery:** Reclassify historical sessions using the stricter definition, recompute cycle counts and confidence, and remove false full-capacity anchors.

**Phase mapping:** Phase A characterizes charge signaling; Phase C formalizes sessions/cycles; Phase D uses only qualified cycles for calibration; Phase F tests partial and interrupted charging.

**Confidence:** HIGH for the modeling rule; MEDIUM for device-specific full-charge evidence.

### Pitfall 15: Letting old calibration dominate after battery aging, firmware change, or behavior drift

**What goes wrong:** Early history overwhelms recent evidence even as usable capacity changes, firmware reporting behavior changes, or the user's activity mix shifts. The estimator appears stable but becomes systematically biased.

**Warning signs:** Recent holdout error grows while lifetime-average confidence remains high; predictions consistently overrun at low percentage; all profiles drift in the same direction after a software/firmware update; residuals correlate with data age.

**Prevention:** Store app/protocol/firmware identifiers when observable, retain event timestamps, weight recent independent sessions more strongly, and run change-point/drift checks. Separate model version from profile identity so an estimator upgrade can rebuild without creating fake settings profiles. Confidence should decay when recent validation is absent.

**Recovery:** Start a new model epoch while retaining raw history, lower confidence, and blend back only if recent validation shows compatibility. Do not erase old evidence until migration/rebuild is verified.

**Phase mapping:** Phase C stores provenance/model version; Phase D implements recency and drift; Phase F includes long-running synthetic replay and upgrade fixtures.

**Confidence:** MEDIUM — direction is well established, but the relevant time scale for this mouse is unknown.

## Minor Pitfalls

### Pitfall 16: Showing stale precision in the tray tooltip

**What goes wrong:** The tray shows “4 h 17 min” from an hours-old sample or a low-confidence model, creating false trust even if the detailed window contains caveats.

**Warning signs:** Minute-level output before calibration; no sample age; the tray value remains unchanged through disconnect; tooltip and detailed view disagree.

**Prevention:** Round estimates to evidence-supported precision, attach calibration/stale state, and prefer ranges or “calculating” when uncertainty is broad. Use one shared presentation model for tray and detailed UI.

**Recovery:** Invalidate cached presentation on every collector-state transition and recompute from the same snapshot used by the detailed window.

**Phase mapping:** Phase D defines precision policy; Phase E applies it consistently; Phase F snapshots stale/disconnected UI states.

**Confidence:** HIGH.

### Pitfall 17: Logging sensitive or unbounded diagnostic data

**What goes wrong:** A background app grows logs indefinitely or records unrelated HID enumeration details from other devices, contradicting the local/privacy and low-resource goals.

**Warning signs:** Logs contain every HID device path; disk usage grows with poll frequency; raw report buffers are logged permanently in normal mode.

**Prevention:** Log only the selected device/interface and parsed protocol diagnostics by default, rotate with a strict size/count limit, redact stable device identifiers where not required, and gate raw-report capture behind a temporary diagnostic mode.

**Recovery:** Rotate/delete excess application-owned logs, disable diagnostic mode automatically, and preserve only aggregate error counters needed for support.

**Phase mapping:** Phase B defines structured diagnostics; Phase E exposes temporary diagnostics; Phase F verifies retention bounds.

**Confidence:** HIGH.

## Early Detection Instrumentation

Build these counters and diagnostics before the estimator UI. They turn subtle model corruption into testable failures:

| Signal | Detects | Release expectation |
|--------|---------|---------------------|
| Percentage delta/plateau histogram by firmware/profile | Coarse or stale reporting | Known distribution from real-device traces; estimator tests use the observed granularity. |
| Observation eligibility counts by exclusion reason | Silent contamination | Charging, sleep, disconnect, profile-unknown, invalid-response, and long-gap exclusions are visible and nonzero in fault tests. |
| HID operation latency, overlap count, open/reopen count, last error | Concurrency and aggressive polling | Overlap count is zero; retries are bounded; vendor-app and reconnect tests recover without tight loops. |
| Profile creations/day and samples/profile | Fragmentation | Deliberate setting changes create one stable profile each; transient unknowns create none. |
| Independent transitions, eligible exposure, sessions, charge-range coverage | False confidence | Confidence cannot rise from duplicate equal readings alone. |
| Rolling temporal holdout error and interval coverage | Miscalibrated ETA | Confidence tier is downgraded automatically when recent coverage fails its contract. |
| Wall-time delta versus awake-time delta | Sleep/clock discontinuity | Large differences force segmentation or a sleep regime, never active attribution. |
| Database schema/model version, last successful migration, integrity result | Corruption and upgrade failure | Startup refuses silent destructive reset and can rebuild projections from raw events. |
| Alert latch, last alerted cycle/threshold, suppression reason | Notification fatigue | At most the designed number of alerts per discharge cycle; suppressed toast leaves persistent status. |
| Last valid sample age and collector state | Stale UI | Tray and detail view use the same state and never render failure as 0%. |

## Roadmap Guardrails

1. **Do not put estimator polish before collector truth.** Phases A–C must land first because model quality cannot exceed the observation and provenance quality.
2. **Make raw evidence replayable.** Every estimator/profile rule is provisional until multiple real charge/discharge traces exist; roadmap acceptance should require deterministic replay into rebuilt projections.
3. **Treat lifecycle boundaries as domain events.** Suspend, resume, disconnect, reconnect, charge transition, profile change, and process restart are not generic errors; they determine whether an interval is learnable.
4. **Make uncertainty a tested output.** Accuracy tests must cover interval calibration and stale/provisional states, not only point-estimate mean error.
5. **Defer notification and startup defaults until persistence exists.** Alert deduplication and user-respected startup state both require durable state across restart.
6. **Require hardware soak gates.** Simulated fixtures are necessary but cannot establish firmware granularity, latency impact, coexistence, charging lag, or actual sleep behavior.

## Remaining Research Gaps

- The actual R5 Ultra percentage step size, rounding policy, update cadence, and low-battery behavior are unmeasured across a full discharge.
- Charging-flag latency, post-charge rebound, and the device's meaning of `100%` require controlled traces.
- The official vendor app's sharing mode and whether simultaneous feature-report requests are safe must be tested, not inferred.
- An independent, low-overhead signal for “active play” versus ordinary use/idle has not yet been selected.
- The storage implementation is not yet fixed; SQLite-specific warnings apply only if that stack is selected.
- Meaningful confidence thresholds require several independent real-device sessions and temporal holdout evaluation.
